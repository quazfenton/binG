# Audit: Root Causes — 2026-07-30

## Confirmed Root Causes

### 1. bash_execute blocks while allocating a sandbox

**File:** `web/lib/bash/bash-tool.ts:660-697`

The current live hang occurs before local process execution.

`trySandboxRoute()` performs two unbounded awaits:

```
await sandboxBridge.getOrCreateSession(agentId);
await sandboxBridge.executeCommand(...);
```

Although `trySandboxRoute` receives a `timeout`, it never applies that timeout to either operation. In the live run:
- Bash execution requested was logged.
- No `sandbox-acquired`, `sandbox-failed`, or `local-spawn` event followed.
- The chat route watchdog fired roughly 130 seconds later.

Therefore the immediate block is sandbox acquisition (or less likely sandbox execution) waiting indefinitely.

**Improvement needed:**
- Bound sandbox acquisition separately, likely to 5–15 seconds.
- Bound sandbox command execution using the requested command timeout.
- Abort sandbox operations when the request signal aborts.
- Fall back to local execution only when that execution environment is valid.
- Emit separate events for: allocation started, allocation timed out, sandbox acquired, command started, command timed out, local fallback selected.

### 2. VFS workspace and command workspace are not synchronized

**File:** `web/lib/bash/bash-tool.ts:898-900` (pre-execution hook), `:1332-1374` (post-execution sync)

The LLM's file tools write into VFS, while Bash executes in a filesystem working directory. There is no complete synchronization step connecting them.

The pre-execution hook is called, but no built-in hook materializes the current VFS snapshot into the sandbox/local directory before execution.

The post-execution sync is also incomplete:
- Only discovers files from shell redirection syntax (`> file`).
- Does not discover files created by npm, Python, build tools, generators, or arbitrary subprocesses.
- Does not synchronize modified or deleted files.
- Defaults to the generic workspace scope because `hookCtx` is created without `scopePath`.
- Does not perform a recursive diff between pre- and post-command workspace state.

**Improvement needed — explicit lifecycle:**
```
┌───────────────┐
│ VFS workspace │
└───────┬───────┘
        │ materialize exact session snapshot
        ▼
┌───────────────────┐
│ Sandbox workspace │
└─────────┬─────────┘
          │ execute command
          ▼
┌───────────────────┐
│ Filesystem diff   │
└─────────┬─────────┘
          │ changed/new/deleted files
          ▼
┌───────────────┐
│ VFS workspace │
└───────────────┘
```
Needs version-aware conflict handling so command results do not overwrite a concurrent VFS edit.

### 3. The requested scope and resolved conversation have two identities

**File:** `web/app/api/chat/route.ts:1091-1144`

The route can resolve a conversation to `018` while honoring a requested scope such as `workspace/sessions/agency-...`. Some downstream paths use `config.scopePath`, but other file tools still produce paths under `sessions/018`.

The system carries:
- logical conversation ID: `018`
- requested workspace scope: `agency-...`
- anonymous owner ID
- sandbox thread/session ID

These are not represented by one canonical request-scoped object.

**Improvement needed — one immutable execution context:**
```ts
{
  ownerId,
  conversationId,
  scopePath,
  sandboxSessionId,
  requestId,
}
```
Every VFS, Bash, sandbox, context-retrieval, reviewer, and SSE path should receive that object.

### 4. Review only runs after modified-file steps

**File:** `packages/shared/agent/orchestration/plan-act-verify.ts:813-861`

Verification and review run only inside `if (modifiedFiles.length > 0)`. Therefore there is no reviewer for steps that:
- execute a command
- run tests
- start a server
- inspect output
- call an integration
- fail every tool call
- return only prose
- claim success without producing a file

This is why the model could say it would "simulate the output" after every `bash_execute` failed.

**Improvement needed — run review for every planned step:**
- file step → current file contents and versions
- command step → command, exit code, stdout, stderr
- server step → PID, port, health probe, HTTP response
- integration step → tool result and external operation identifier
- read-only step → retrieved evidence
- failed step → tool errors and unresolved acceptance criteria

---

### 5. Tool failures do not automatically fail the current plan step

**File:** `packages/shared/agent/orchestration/plan-act-verify.ts:705-750`, `:863`

Tool validation and execution failures are added to history, but the step can still advance at step 863. There is no general invariant such as:

*"If a required tool failed and no later equivalent tool succeeded, the step remains incomplete."*

The only specialized failure feedback is for search tools.

**Improvement needed — per-step evidence record:**
```ts
{
  requiredCapabilities,
  attempts,
  successfulResults,
  failedResults,
  modifiedFiles,
  acceptanceCriteria,
  status,
}
```
Before incrementing `stepIndex`, evaluate whether evidence satisfies the step.

---

### 6. Final summarization can invent completion

**File:** `packages/shared/agent/orchestration/plan-act-verify.ts:866-875`

The final response asks the same LLM to "Summarize the completed work." It does not provide a canonical completion ledger distinguishing passed steps, failed steps, skipped steps, unverified claims, and artifacts actually produced.

This allows the final model call to phrase partial or failed execution as success.

**Improvement needed — deterministic completion status:**
```ts
{
  overallStatus: 'failed',
  completed: ['created hello.py'],
  failed: ['execute python3 hello.py'],
  unverified: ['stdout equals AGENCY_EXEC_OK'],
}
```
The model may turn that state into prose, but must not decide what succeeded.

### 7. Anonymous cookies are missing on some streaming exits

**Files:**
- `web/app/api/chat/route.ts:5197-5213` (main stream — has Set-Cookie)
- `web/app/api/chat/route.ts:1487-1505` (local V2 stream — missing)
- `web/app/api/chat/route.ts:3138-3147` (another stream return — missing)

The owner resolver correctly returns a new anonymous ID at `resolve-filesystem-owner.ts:95-124`, but each response branch must apply it.

**Improvement needed — one response-header builder for every SSE response:**
Always add:
- anonymous cookie when newly created
- anonymous session response header
- CORS headers
- stall metadata
- no-buffer/cache headers

---

### 8. Auto-continue message format is fragile

**File:** `web/app/api/chat/route.ts:2813-2846` (history assembly), `:2858` (loop)

Continuation history is manually assembled with legacy-looking fields:
```ts
{ role: 'tool', tool_call_id: ..., content: ... }
```

Elsewhere, the code documents that AI SDK v6 expects typed tool-result content parts. The live Google run produced: *"Please ensure that function call turn comes immediately after a user turn."*

**Improvement needed — canonical AI SDK message builder:**
```ts
{
  role: 'tool',
  content: [{
    type: 'tool-result',
    toolCallId,
    toolName,
    output: { type: 'json', value: result },
  }],
}
```

---

### 9. Continuation loop lacks explicit cap termination semantics

**File:** `web/app/api/chat/route.ts:2449-2477`

The loop stops when iteration reaches `LLM_AGENT_TOOLS_MAX_ITERATIONS`, but does not clearly produce:
- a cap-reached event
- an incomplete status
- unresolved acceptance criteria
- a reason why continuation stopped

Surrounding comments still describe the old `do/while(false)` behavior.

**Improvement needed when cap is reached:**
- emit `continuation_exhausted`
- mark result incomplete
- prohibit a success summary
- include remaining tasks
- clear continuation counters in a finally block

**File:** `web/lib/orchestra/stateful-agent/agents/stateful-agent.ts:1579-1581`

Still calls `selectToolPlan(userMessage)`. The current API requires `SelectToolPlanInput`.

```ts
selectToolPlan({
  userMessage,
  conversationHistory: [],
  attachedFiles: [],
  authenticated: Boolean(userId),
  filesystemEditEligible: true,
  configuredSources: ...,
});
```

## External / Configuration Defects

These reduce fallback robustness but are not core orchestration bugs:
- Google free-tier quota exhausted during testing
- Mistral returned rate limits
- NVIDIA model rotation selected a model returning HTTP 410
- Arcade key returns HTTP 401
- MCP and Composio initialize with zero tools
- A configured V2 gateway is unreachable, adding a failed request before V1 fallback
- Mem0 occasionally consumes its full timeout budget

The provider ranker should immediately suppress known quota-exhausted, unauthorized, or gone models rather than repeatedly selecting them during the same workflow.

---

## Recommended Repair Order

1. Bound sandbox allocation/execution and honor cancellation.
2. Implement bidirectional VFS ↔ execution-workspace synchronization.
3. Canonicalize owner/conversation/scope/sandbox identity.
4. Require deterministic evidence before a plan step can pass.
5. Run reviewer checks for command, server, and integration steps — not only file edits.
6. Replace continuation history with valid AI SDK tool-call/result messages.
7. Centralize streaming response headers and anonymous cookies.
8. Fix the stale `selectToolPlan` call.
9. Add artifact-backed E2E coverage for Python, npm build/test, server preview, repeat edit, and command failure recovery.
