# `.postaudit-baseline.json` schema reference

Canonical schema for the postaudit acceptance baseline file. The TypeScript
interface (`Baseline` in `postaudit-baseline.test.ts`) is the source of
truth — this file is the operator-facing copy-paste reference.

## Top-level shape

```ts
{
  version: string;              // ISO-date style, e.g. "2026-07-16.1"
  capturedAt: string;            // ISO-8601 timestamp
  postauditAcceptanceFiles: string[];  // vitest positional args
  summary: {
    numTotalTests: number;
    numPassedTests: number;
    numFailedTests: number;
    numSkippedTests: number;
  };
  trackedSkipped: BaselineTrackedTest[];  // intentionally-skipped tests
  trackedFailed: BaselineTrackedTest[];   // intentionally-failing tests
  acknowledgedOrphans: AcknowledgedOrphan[];  // operator-confirmed removals
  thresholds: {
    minTotalTests: number;
    minPassedTests: number;
    maxFailedTests: number;
    maxUntrackedSkippedTests: number;
    maxUntrackedFailedTests: number;
  };
}

interface BaselineTrackedTest {
  file: string;       // relative path from web/ (e.g. "__tests__/tools/select-tool-plan.test.ts")
  testPath: string;   // vitest fullName (e.g. "describe > nested > it")
  ticket: string;     // reference (e.g. "bing/.tickets/STALL-ROUTEINTEGRATION-FOLLOWUP.md")
}

interface AcknowledgedOrphan extends BaselineTrackedTest {
  acknowledgedAt: string;  // ISO-8601 timestamp of when removal was acknowledged
  reason: string;          // free-text explanation of WHY the test was removed
}
```

## Operator workflow — adding an `acknowledgedOrphans` entry

When you intentionally delete or refactor a tracked test (one in
`trackedSkipped` or `trackedFailed`), the orphan-detection test will
hard-fail unless you do ONE of:

1. **Restore the test to source** — preferred when the deletion was accidental
2. **Add an `acknowledgedOrphans` entry** — preserves the audit trail of WHY the
   test was removed (preferred when the deletion was intentional and the test
   is permanently gone)
3. **Delete the orphaned entry from `trackedSkipped` / `trackedFailed`** — loses
   the audit trail but acceptable when the removal was unintentional cleanup

### Copy-paste example

The example below is **parseable JSON** — every field is filled in with
valid syntax, but `trackedSkipped` + `trackedFailed` + `summary` + `thresholds`

values with the file's CURRENT values. ONLY the `acknowledgedOrphans`
array slot is the editable target for adding a new entry.

reference; replace it with your actual ticket path (or full URL for

editable target.

### Field rules

| Field | Format | Required | Notes |
|---|---|---|---|
| `file` | relative path from `web/` | yes | Match the exact value in `trackedSkipped` / `trackedFailed` |
| `testPath` | vitest `fullName` | yes | `describe-block > nested-block > it-name`. Whitespace must match exactly |
| `ticket` | path or URL | yes | Cross-reference to the ticket explaining the intent. Use `bing/.tickets/...` for in-repo tickets, full URLs for external trackers |
| `acknowledgedAt` | ISO-8601 with `Z` timezone | yes | UTC preferred for consistency with `capturedAt`. Format: `YYYY-MM-DDTHH:MM:SSZ` |
| `reason` | free-text, ≤500 chars recommended | yes | Explain WHY the test was removed. Include the commit hash if removal was landed in a specific commit. Operators grepping the audit trail 6 months from now need this to understand the intent |

## How orphan-detection works

The test in `postaudit-baseline.test.ts`:

1. Builds a `Set` of `file::testPath` keys for every test in the current vitest run
2. For each entry in `trackedSkipped` + `trackedFailed`, checks if its
   `file::testPath` key is in the current run's set
3. If NOT in the current run (i.e., the test was removed from source):
   - If the key IS in `acknowledgedOrphans` → log as `ACKNOWLEDGED ORPHAN (informational, no failure)`
   - If the key is NOT in `acknowledgedOrphans` → log as `UNTRACKED ORPHAN` + hard-fail

The hard-fail message tells the operator exactly which remediation path to take:

```
UNTRACKED ORPHAN: __tests__/foo.test.ts > bar > baz
  → restore the test to source
  → OR add an entry to baseline.acknowledgedOrphans with reason
  → OR delete this entry from baseline if removal was unintentional cleanup
```

## CI behavior

`pnpm test` runs the chain:
1. Main suite (all tests except postaudit-baseline — excluded via dynamic argv-gate)
2. Audit-recs family (cite-drift, finding-1, finding-2, finding-5-6, postaudit-baseline)

The `postaudit-baseline` test is the regression guard. Its 6 assertions
fire ONLY against the 7 postaudit acceptance files (not the full suite),
keeping CI runtime bounded (~8s) regardless of how large the main suite grows.

## Versioning

Bump `version` (e.g. `2026-07-16.1` → `2026-07-16.2`) whenever the
schema changes shape. The `version` field is currently informational —
no migration logic depends on it. If schema-migration logic is added
later, bump `version` and write a migration shim in `postaudit-baseline.test.ts`.

## Quick-verify after edit

After modifying `.postaudit-baseline.json`, sanity-check your edit
before committing:

```bash
cd /opt/bing/web && npx vitest run __tests__/audit-recs/postaudit-baseline.test.ts
```

Expected output: `6/6 tests passed` in ~8s. If the test fails, consult one of the two tables below depending on whether the failure is loud (CI red) or silent (CI green but log messages indicate trouble).

### Hard-fail patterns (CI red — visible failure)

| Failure pattern | Likely cause | Remediation |
|---|---|---|
| `INVALID JSON` parse error in console output | Syntax error in your edit (extra comma, unclosed bracket) | Run `node -e "JSON.parse(require('fs').readFileSync('.postaudit-baseline.json','utf8'))"` to localize the syntax error (it'll print the exact line/column) |
| `UNTRACKED ORPHAN: ...` | The `acknowledgedOrphans` entry's `file::testPath` doesn't match any entry in `trackedSkipped` / `trackedFailed` | Verify the `testPath` matches the vitest `fullName` exactly (whitespace + `>` separators); if mismatch, fix it. If the test was intentionally removed from source, either add an `acknowledgedOrphans` entry (preserves audit trail) or delete the orphaned entry from `trackedSkipped` / `trackedFailed` (acceptable for unintentional cleanup) |
| `trackedSkipped → now passing` log | A tracked-skipped test now passes (POSITIVE change, no failure) | Remove the entry from `trackedSkipped` + commit the intent (operator confirmed the skip is no longer needed). The guard already reported the fix in console output. |
| `numPassedTests` dropped below threshold | Regression in the 7 postaudit acceptance files (untracked test deletion or new failures) | Run `cd /opt/bing/web && pnpm test:postaudit-baseline` standalone for the failure detail (it spawns a child vitest with `--reporter=json` so the failing assertion IDs are grep-able). If regression is real, fix the failing source file. If test was intentionally removed, hand-edit `summary.numPassedTests` + `summary.numTotalTests` + `thresholds.minPassedTests` + `thresholds.minTotalTests` in a separate commit with a clear message explaining the intentional change |

### Silent-corruption patterns (CI green but log indicates trouble — manual discipline required)

| Failure pattern | Likely cause | Remediation |
|---|---|---|
| ISO-8601 missing `Z` suffix | `acknowledgedAt: "2026-07-16T13:45:00"` instead of `"2026-07-16T13:45:00Z"` — JSON parses but breaks UTC consistency with `capturedAt`. CI doesn't fail (string type accepts both) but audit-trail sort order is broken | Always include the `Z` suffix for UTC consistency; canonical format: `YYYY-MM-DDTHH:MM:SSZ` (matches `capturedAt`) |
| Bare ticket slug without path | `ticket: "STALL-123"` instead of `ticket: "bing/.tickets/STALL-123.md"` — CI doesn't fail (string type accepts both) but audit trail is unclear (which tracker? which repo? which ticket-system?) | Use the full relative path from repo root (e.g. `bing/.tickets/STALL-123.md`); or full URL for external trackers (GitHub / Linear / Jira) |

**Why two tables?** Hard-fail patterns are CI-enforced (CI turns red); silent-corruption patterns are NOT caught by CI and require manual discipline via code review or vitest console inspection. Operators should catch them preemptively rather than discovering broken sort order or missing ticket path months later during audit.
